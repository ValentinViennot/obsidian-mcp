Refs #350

## Why

The server has no way to ask "which tasks are open". `keyword_search` cannot match `- [ ]` because the tsvector drops punctuation, `semantic_search` ranks prose rather than enumerating checkboxes, and an MCP-only client has no Grep. So an agent that wants the open tasks reads every note that might hold one. The 2026-10-23 incident (PR #337) was an agent gateway's morning briefing doing exactly that: about 400 `read_note` calls in about 100 s against 21 task files reached through a task index note. That index note is made entirely of Tasks-plugin query blocks, which are literal text to this server. The fix that shipped raised the velocity buckets, which treated the symptom. The vault is Max's single source of truth for every project, so the tasks in it are something agents need to query directly, in one bounded call.

## What Changes

- **A new derived table, `note_tasks` (migration 032)**, written by the index pass in the same per-note step and the same transaction as `note_links`. One row per checkbox list item in a note body: the owning note's id (FK, `ON DELETE CASCADE`), its 1-based line in the file, the raw status character, a derived `state` (`open` / `done` / `cancelled`), the task text (capped at 1,000 characters, with a cut flag), the Tasks-plugin dates (due 📅, scheduled ⏳, start 🛫, done ✅) parsed from `YYYY-MM-DD`, the priority (🔺 ⏫ 🔼 🔽 ⏬), inline `#tags` (the first 64 distinct in document order, with a `tags_cut` flag), and the heading path the item sits under. The table stores no path and no owner. Both come from the note's row through the join, so a task row cannot outlive its note, cannot exist before it, and follows an id-preserving move without being rewritten.
- **`notes_metadata.tasks_truncated` (migration 032)**, which works like `links_truncated`. Task extraction is capped per note at `MAX_TASKS_PER_NOTE` (5,000), and a capped note is marked on its row and reported by the tool. The cap is not a skip. A third column, `notes_metadata.tasks_failed`, marks a note whose task derivation failed. A task failure is isolated to that note's task rows and **never** quarantines, prunes or fails the note or the pass, and every `list_tasks` header counts such notes.
- **A fence-aware task extractor** in a new module, `src/services/tasks.py`. It runs over the shared `code-masking` grammar, so a checkbox inside a fenced block (or a fence inside a list item) is not a task. A checkbox marker that inline-code masking changed is not a task either, which is the #218 rule for links applied here. Headings come from the shared column-zero ATX rule, and tags from the shared inline-tag rule. Tasks-plugin query blocks are never evaluated. An invalid date (`📅 2026-02-30`) stores NULL and keeps the text. It never fails the note.
- **The extraction version moves to 4**, which is the established backfill mechanism (#150, #203, #218). The first pass after deploy re-derives every note once, so every existing note gains its task rows. Version 4 shares version 3's embedding cleaner, so **no note is re-embedded**.
- **The indexer gains a second per-note derivation beside the link rebuild**, `_update_tasks_for_changed`. It follows the link rebuild's contract exactly: it reads only the scan's buffered bodies, deletes and reinserts per changed note in the pass transaction, and records missing-buffer skips in the same lists that withhold a re-derive's stamp. It departs from the link rebuild in one place: each note's task rows are written in their own savepoint, and a failure is retried once and then recorded as `tasks_failed`. It is never sent to the poison-note quarantine (Codex spec round 1). The seam is written so that a third derivation (the `change-feed` change, #351) can be added next to it without touching either of the first two.
- **A new read tool, `list_tasks(folder?, status="open", due_by?, scheduled_by?, tags?, limit=100, cursor?)`**. It is registered with `title="List tasks"` and the shared read-only `ToolAnnotations`, wrapped by `_tracked`, and placed in concurrency class `scan`. It is scoped to the caller's vault through the total owner mapping, bounded by `limit` (cap 500) and by the response-character cap, with an abbreviated first row so that every page makes progress, and paged with a keyset `next` cursor over `(due, path, line)`. The cursor is bound to the caller's owner scope and filters, never carries a database id, and uses `'infinity'::date` for undated tasks. The `tags` argument is validated in the body (at most 32 tags of 1–128 characters). Each task renders as exactly one server-authored line, and every note-controlled field passes through the one-line rule, so a note cannot forge a result row. The header always carries the counts of notes not yet scanned for tasks, notes whose tasks could not be indexed, and capped notes, and with `tags=` the count of tasks whose tags were cut. Each count is stated even when it is zero.
- **Agent guidance**: the vault-guide primer's Tasks section and the server instructions each gain one neutral sentence that points at `list_tasks` instead of scanning notes.
- **Documentation in the same PR**: README tool list, CLAUDE.md "MCP tools" section, `docs/architecture/indexing-and-embeddings.md`, `docs/architecture/vault-tools.md`, `docs/architecture/schema-and-migrations.md` (032, plus `note_tasks` in the derived-tables list).

Read-only. No task toggling, no Tasks-plugin query evaluation, no recurrence expansion. A frontmatter query (#352) does not cover this case, because tasks live in note bodies.

## Capabilities

### New Capabilities

- `note-tasks`: task extraction grammar (checkbox shape, status mapping, Tasks-plugin fields, fence awareness, caps), the `note_tasks` derived-state lifecycle in the index pass, and the `list_tasks` tool contract (arguments, ordering, cursor, rendering, bounds, tenancy).

### Modified Capabilities

- `index-integrity`: ADDED "A task-derivation failure SHALL be isolated to that note's task rows and SHALL NOT quarantine, prune or fail anything else". The quarantine requirement itself is unchanged.
- `note-filters`: MODIFIED "Read-path owner scoping is total". `list_tasks` joins the list of index-backed read tools.
- `vault-guide`: ADDED "Guide points at `list_tasks` for task queries".
- `schema-integrity`: ADDED "Migration 032 SHALL own the task table and the task-truncation column as marked units".
- `mcp-request-routing`: MODIFIED "Every registered tool SHALL publish a title and a complete set of behaviour annotations" (26 tools, `list_tasks` among the sixteen read-only) and "Tool metadata SHALL leave the published tool surface otherwise unchanged" (the 5a391ca fixture stays frozen for the first 25 entries, and a deliberately generated additions fixture holds `list_tasks`).

## Impact

- **Schema**: migration 032 (`alembic/versions/032_note_tasks.py`), one table and two columns with server defaults. It is metadata-only on `notes_metadata` and has no backfill in SQL. `change-feed` (#351) owns 033.
- **Code**: `src/services/tasks.py` (new), `src/services/indexer.py` (version 4, buffered line offset, `_update_tasks_for_changed`, per-note failure isolation), `src/services/embeddings.py` (version 4 cleaner alias), `src/models/db.py` (`NoteTask`, `tasks_truncated`, `tasks_failed`), `src/config.py` (`MAX_TASKS_PER_NOTE`, `TASK_TEXT_MAX_CHARS`, `TASK_TAG_MAX_CHARS`, `TASK_MAX_TAGS`, `LIST_TASKS_MAX_TAG_ARGS`), `src/mcp_server/tools.py` (`list_tasks_impl`, renderer), `src/mcp_server/server.py` (registration, instructions sentence), `src/mcp_server/vault_guide_primer.md`, `src/services/concurrency.py` (`list_tasks: scan`, `CLASS_MAPPING_VERSION` 2 → 3).
- **Tests**: unit tests for the extractor, renderer and cursor; integration tests (guarded on `PGVECTOR_TEST_ADMIN_URL`) for lifecycle, moves, prune, quarantine, re-derive and tenancy; the pinned tool counts and fixture (design D12: `test_issue_343_tool_metadata.py`, `test_issue_295_unknown_arguments.py`, `test_issue_263_coverage_registry.py`, `test_issue_261_controller.py`, `test_issue_261_tool_admission.py`, plus the new `tools_list_schema_additions.json`); `tests/test_backup_derived_tables.py` (`note_tasks` is derived).
- **Operations**: one full re-derive pass after deploy, the same cost as the version 2 and 3 bumps. During that window `move_note(rewrite_links=True)` refuses as it does today on a stale extraction marker. `CLASS_MAPPING_VERSION` 3 starts a new concurrency-readiness epoch, so `make concurrency-report` evidence gathered under 2 does not carry over. No new setting reaches `.env` (both caps are constants), so `.env.example` and the README settings tables are unchanged.
- **Coordination with #351 (`change-feed`)**: the two changes touch the same indexer step. Each one bumps `CLASS_MAPPING_VERSION` if it adds a tool, so whichever merges second takes the next value. The version 4 re-derive marks every note as changed for one pass, so a change feed fed from the pass's changed set must not report that pass's marker-stale notes as content changes. See design D10.
